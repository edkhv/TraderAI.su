# Архитектурный обзор

Это публичное описание логических границ платформы. Оно не раскрывает
производственную реализацию или торговые правила.

## Публичный слой — реализован здесь

```text
Посетитель → HTTPS / reverse proxy → статические HTML + CSS + JS
                                      └→ демо в памяти браузера
```

Astro строит готовые HTML-страницы. TypeScript обслуживает учебный
интерактивный процесс и необязательные короткие анимации. Нет серверного API, общей сети с исследовательским
приложением, доступа к моделям, данным пользователей или брокерам.

## Исследовательские направления

Описанные ниже модули — целевая архитектура, развиваемая на основе
исследовательских прототипов. Они не реализованы как рабочие интеграции в этом
репозитории. Схемы не задают количество сервисов или используемых моделей.

### 1. RAG в контексте отдельной стратегии

Для каждой авторской стратегии проектируется собственная база знаний.
В неё входят разрешённые видео, правила, словарь терминов, планы и примеры.
RAG означает поиск релевантных фрагментов перед генерацией ответа, а не
переобучение модели на каждом новом материале.

```text
Пользователь + права → выбранные автор / стратегия / версия
→ поиск только в разрешённом контексте
→ фрагменты + ссылки + ограничения → объяснение
```

Логическая граница поиска обязательна: сходство текста само по себе не
разрешает использовать правило другой методики или устаревшую версию.
Новый материал должен иметь происхождение и статус, а противоречие с
утверждённым правилом требует рассмотрения. Конкретный способ физического
хранения не предписывается этой публичной схемой.

### 2. Обработка видео и поиск

```text
Разрешённый материал → очередь → подготовка аудио → ASR
→ фрагменты с таймкодами + дополнительный контекст кадров
→ семантический и текстовый индекс → поиск → optional reranking
→ ответ + источники + ограничения вывода
```

FFmpeg подготавливает медиа; ASR преобразует речь в текст. Эмбеддинги
помогают искать по смыслу, текстовый поиск — по терминам и точным формулировкам.
Дополнительное ранжирование необязательно. Статус обработки должен показывать,
какие материалы уже доступны для поиска, а какие ещё не прошли индексацию.

Таймкоды наследуются от материала, не создаются моделью. Без достаточных
источников система должна сообщать об отсутствии основания. Визуальная
информация графика рассматривается как дополнительный контекст с ограниченной
надёжностью. Индексируемый текст не получает полномочий системной инструкции.

### 3. ИИ-агенты и формализация

| Роль          | Вход и инструменты                          | Проверяемый результат                              |
| ------------- | ------------------------------------------- | -------------------------------------------------- |
| Исследователь | Вопрос, разрешённая база стратегии, поиск   | Объяснение со ссылками или указание на пробел      |
| Формализатор  | План, термины и утверждённые правила        | Проект условий и вопросы к неоднозначностям        |
| Наблюдатель   | События программного монитора, версия плана | Объяснение связи события с условиями и источниками |
| Аналитик      | Журнал, рассчитанные метрики, правила       | Разбор отклонений и гипотеза для испытания         |

Агентные роли задают ограниченные инструменты и ответственность, а не
обязательную отдельную модель для каждого шага. Обмен строится вокруг
структурированных результатов с известным происхождением. Числовые
проверки рынка и риска не делегируются свободному рассуждению LLM.

```text
Описание автора → проект условий → неоднозначности и вопросы
→ рассмотрение человеком → утверждённая версия → наблюдение за событиями
```

Модель не должна восстанавливать неизвестное правило как установленный факт.
Новая версия не подменяет старую. Ручное решение может оставаться
дискреционным, но воспроизведение требует однозначных полномочий и ограничений.

### 4. Управление через Telegram

Бот — интерфейс к тем же знаниям и операциям, которые контролирует прикладной
слой. Он не создаёт отдельный обход проверок.

```text
Сообщение → проверка пользователя и полномочий
→ выбранная стратегия и операция → прикладной API / очередь
→ результат или статус → ответ / уведомление
```

Сценарии: задать вопрос по методике; найти фрагмент видео; передать разрешённый
материал и узнать статус обработки; разобрать и уточнить план; получить
уведомление о сигнале или отказе; запросить журнал и отчёт за период.
Диалог на сайте — иллюстрация концепции, не подключённый бот.

Доступ к чужим материалам нельзя выводить из текста сообщения. Значимые
операции требуют проверки полномочий, текущей версии и предусмотренного
подтверждения. При проектировании обработки команд также необходима защита
от повторного исполнения одного запроса.

### 5. Журнал и анализ сделок

Запись связывает стратегию и её версию, план, источник, рыночный контекст,
сигнал, проверки, исход и основания отказа. Виртуальные сделки и будущие
реальные исполнения должны различаться явно. Отсутствие сделки — тоже
результат, если система отказала или запросила уточнение.

Программный слой рассчитывает результат после издержек, просадку, долю
успешных сделок, средний результат и результат в единицах исходного риска
(R). Анализ возможен по инструментам, сценариям, схемам выхода, периодам и
версиям. Разные правила не смешиваются без явной маркировки.

ИИ объясняет уже рассчитанные значения, помогает сопоставить план с фактом
и сформулировать вопросы. Он не является источником числового P&L.
В этом репозитории нет реальных сделок и статистики стратегии.

### 6. Рекомендации и версии

```text
Наблюдение + записи журнала + правила → проект гипотезы
→ рассмотрение человеком → отдельный эксперимент
→ оценка результата → решение о новой версии
```

Рекомендация должна содержать основание, ограничения вывода и план проверки:
например, уточнить недостающее условие, исследовать повторяющееся отклонение
или сравнить способы выхода на отдельном периоде. Недостаточная выборка
должна ограничивать вывод, а не скрываться за уверенностью модели.

Из проекта подсказки нет прямого пути к активным правилам, лимитам и ордерам.
Принятие к исследованию не означает включение в торговлю. Улучшение должно
подтверждаться измерениями; оно не гарантируется самим использованием ИИ.

### 7. Проверки и исследование

```text
Источник решения → проверка происхождения и версии
→ независимые числовые проверки → допуск / отказ / уточнение
→ виртуальная среда → журнал → расчёт → объяснение
```

Реальное исполнение — отдельная граница, отсутствующая в showcase. В
исследовательском контуре реальные действия требуют Risk Guard и ручного
подтверждения. LLM не получает право исполнять поручения.

При историческом испытании факторы должны рассчитываться из данных,
доступных на момент сигнала. Периоды подбора и проверки разделяются;
учитываются издержки и ограничения качества исходных данных.
Виртуальная торговля исследует поведение на поступающих событиях без
движения реального капитала.

## Технологический ландшафт

Python, FastAPI и Pydantic — обработка событий и явные контракты данных;
FFmpeg и ASR — медиа; эмбеддинги, текстовый поиск и LanceDB — поиск знаний;
Telegram Bot API — интерфейс; SQLite — очередь и журнал в исследовательском
контуре. Модели и внешние системы подключаются через ограниченные адаптеры.
Локальные вычисления требуют явной загрузки моделей и контроля памяти.

## Полезные инженерные свойства

| Свойство                        | Зачем                                                     |
| ------------------------------- | --------------------------------------------------------- |
| Происхождение событий           | Можно понять, откуда получен факт                         |
| Версионирование                 | Результаты разных правил не смешиваются                   |
| Неизвестность блокирует допуск  | Нет молчаливой замены отсутствующих данных                |
| Детерминированные расчёты       | Повторяемый результат без зависимости от формулировки LLM |
| Журнал отказов                  | Объясняет также решения ничего не делать                  |
| Раздельные периоды эксперимента | Помогают оценивать переносимость гипотезы                 |
| Учёт издержек                   | Валовый результат не выдаётся за чистый                   |
| Явное управление моделями       | Тяжёлые вычисления не конкурируют бесконтрольно           |

Эти свойства требуют собственной реализации и проверки в платформе. Маленькое
публичное демо иллюстрирует только часть из них и не считается торговым движком.
